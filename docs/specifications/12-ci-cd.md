# 12 - CI/CD (GitHub Actions)

## Overview

CI/CD pipelines are implemented with GitHub Actions. All workflows follow security best practices.

## Workflows

### ci.yml - Continuous Integration

Triggers: `push` to main, `pull_request` to main.

Jobs:

1. **check** - Format check, clippy lint, build
2. **test** - Run tests with coverage
3. **audit** - `cargo audit` for dependency vulnerabilities
4. **race-check** - Thread sanitizer (nightly, Linux only)

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-hash>
      - uses: dtolnay/rust-toolchain@<commit-hash>
        with:
          toolchain: stable
          components: rustfmt, clippy
      - run: cargo fmt --check
      - run: cargo clippy -- -D warnings
      - run: cargo build --release

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-hash>
      - uses: dtolnay/rust-toolchain@<commit-hash>
        with:
          toolchain: stable
      - run: cargo install cargo-tarpaulin
      - run: cargo tarpaulin --out xml --output-dir coverage/
      - name: Upload coverage
        uses: actions/upload-artifact@<commit-hash>
        with:
          name: coverage
          path: coverage/

  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-hash>
      - run: cargo install cargo-audit
      - run: cargo audit

  race-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-hash>
      - uses: dtolnay/rust-toolchain@<commit-hash>
        with:
          toolchain: nightly
      - run: |
          RUSTFLAGS="-Z sanitizer=thread" \
          cargo +nightly test \
          --target x86_64-unknown-linux-gnu
```

### release.yml - Release

Triggers: Push of semver tag (`v*.*.*`).

Jobs:

1. **build** - Cross-compile for all target platforms
2. **release** - Create GitHub Release and upload binaries
3. **homebrew** - Update Homebrew tap formula

Target platforms:

| Target                        | OS      | Arch    |
|-------------------------------|---------|---------|
| `x86_64-unknown-linux-gnu`    | Linux   | x86_64  |
| `aarch64-unknown-linux-gnu`   | Linux   | aarch64 |
| `x86_64-apple-darwin`         | macOS   | x86_64  |
| `aarch64-apple-darwin`        | macOS   | aarch64 |
| `x86_64-pc-windows-msvc`      | Windows | x86_64  |

```yaml
name: Release

on:
  push:
    tags:
      - 'v[0-9]+.[0-9]+.[0-9]+'

permissions:
  contents: write

jobs:
  build:
    strategy:
      matrix:
        include:
          - target: x86_64-unknown-linux-gnu
            os: ubuntu-latest
          - target: aarch64-unknown-linux-gnu
            os: ubuntu-latest
          - target: x86_64-apple-darwin
            os: macos-latest
          - target: aarch64-apple-darwin
            os: macos-latest
          - target: x86_64-pc-windows-msvc
            os: windows-latest
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@<commit-hash>
      - uses: dtolnay/rust-toolchain@<commit-hash>
        with:
          toolchain: stable
          targets: ${{ matrix.target }}
      - run: cargo build --release --target ${{ matrix.target }}
      - uses: actions/upload-artifact@<commit-hash>
        with:
          name: cloudapps-${{ matrix.target }}
          path: target/${{ matrix.target }}/release/cloudapps*

  release:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@<commit-hash>
      - name: Create Release
        uses: softprops/action-gh-release@<commit-hash>
        with:
          files: cloudapps-*/cloudapps*
          generate_release_notes: true
```

## Security Requirements for Workflows

1. Use `pull_request` trigger (never `pull_request_target`).
2. Minimize `permissions` to the least required scope.
3. Pin all third-party actions to commit hashes (not tags).
4. Do not use user-controlled input in shell commands without quoting.
5. Do not expose secrets in logs.
6. Use `cargo audit` to check dependencies.

## Workflow Dependency Lockfile

All workflows are registered in `.github/workflows/actions.lock`, generated by
GitHub's `gh-actions-lock` v0.2.0 (public preview). Keep the existing commit SHA
references and pinact checks; the lockfile additionally records repository
identities and composite-action dependencies. The SLSA reusable workflow keeps
its version tag for provenance verification. **The v0.2.0 generator and verifier
exclude reusable-workflow references**, so the SLSA call is not pinned by this
lockfile. Its internal dependencies are also outside this repository's lockfile.
Revisit this limitation when upgrading the extension; successful `--verify`
does not prove coverage of reusable workflows or successful provenance creation.
See the [v0.2.0 scanner](https://github.com/github/gh-actions-lock/blob/v0.2.0/internal/workflowfile/workflowfile.go)
and its [reference parser](https://github.com/github/actions-lockfile/blob/go/v0.0.6/go/pkg/lockfile/uses.go).

`dtolnay/rust-toolchain` is pinned to a commit on `master`, with each job's
`toolchain` input selecting `stable` or `nightly`. The previous pin from the
generated `stable` branch was rejected as no longer belonging to an upstream
branch or tag. Keep future pins reachable from upstream history.

Install the extension and regenerate the lockfile from the repository root when
adding, removing, or changing workflow dependencies, including new workflows:

```bash
gh extension install github/gh-actions-lock --pin v0.2.0
gh actions-lock --no-narrow
gh actions-lock --verify
actionlint
pinact run --verify --check
```

Commit workflow changes and the generated lockfile together. Do not edit the
lockfile manually. Review changed commits as dependency updates, and investigate
any changes to `owner_id` or `repo_id` before merging. Dependabot updates the
lockfile for onboarded workflows; new workflows still need
`gh actions-lock --no-narrow`. The flag preserves SHA references for pinact;
without it, the generator rewrites them to tags. A bare-SHA advisory from
`--verify` is expected with this policy and does not fail validation.

The `actions-lock.yml` workflow runs `--verify` on workflow and local-action
changes using a versioned, SHA256-verified binary and a read-only token.
`gh actions-lock --verify-local` offers an offline coverage check, but does not
validate repository identities or upstream commits and cannot replace CI's
online verification. Existing pins are retained on normal runs. Use `--relock`
only to adopt reviewed upstream changes; investigate unreachable commits before
considering `--accept-moved`.

Where the preview is supported, GitHub validates onboarded workflows before
execution. Server-side enforcement has not been verified for this repository;
the CI check above independently verifies the lockfile. Repository-wide
Settings > Actions > Policies > Require lockfile is a separate administrative
setting and is not enabled by these files. If an action allowlist is introduced,
use full SHAs or wildcards: tag-only entries do not match locked dependencies.

References: [GitHub documentation](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies)
and [gh-actions-lock](https://github.com/github/gh-actions-lock).

## Semantic Versioning

- Version format: `MAJOR.MINOR.PATCH` (e.g., `1.0.0`).
- Version is defined in `Cargo.toml`.
- Release is triggered by pushing a tag matching `v*.*.*`.
- The tag version must match the `Cargo.toml` version.
